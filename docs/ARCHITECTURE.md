# Architecture

## Scope

This document describes the implemented Phase 1 foundation through the Phase 7 security evaluation pipeline. Red-Team Arena can generate one controlled adversarial test prompt, test defensive input/output controls, and evaluate one already-produced interaction, but it does not yet execute a target assessment or orchestrate duels.

## Implemented application foundation

The repository is a small monorepo with independently runnable applications:

- `apps/web` is a Next.js App Router application written in TypeScript and styled with Tailwind CSS. Its developer-facing page calls the backend health endpoint and reports whether the API is reachable.
- `apps/api` is a FastAPI application. Versioned routes live under `/api/v1`; it exposes health checks plus isolated development routes for registered-model, Red Agent, guardrail, and evaluation testing.
- SQLAlchemy provides an async engine and sessions using the `asyncpg` PostgreSQL driver. The database health check executes `SELECT 1` against a real session.
- Alembic imports the shared SQLAlchemy metadata and obtains its connection URL from application settings.
- `infra/compose.yaml` runs PostgreSQL for local development with a persistent named volume.

```text
Browser (Next.js :3000)
        |
        | GET /api/v1/health
        v
FastAPI (:8000) -------- SQLAlchemy async engine -------- PostgreSQL (:5432)
        |
        +-------- environment-based settings
```

### Configuration boundary

The API loads settings from environment variables, with the repository-root `.env` file as a development convenience. CORS accepts the configured `FRONTEND_URL` origins and does not use a wildcard origin.

Browser-visible Next.js configuration uses `NEXT_PUBLIC_API_URL`, defaulting to `http://localhost:8000`.

### Backend module boundaries

- `app/api` owns HTTP routing and HTTP responses.
- `app/core` owns cross-cutting configuration.
- `app/db` owns SQLAlchemy metadata, engine creation, and session lifecycle.
- `app/domain` owns framework-independent enums and domain values.
- `app/models` owns relational persistence models and relationships.
- `app/schemas` owns Pydantic input and output validation structures.
- `app/model_gateway` owns provider-independent execution contracts, errors, gateway behavior, and provider adapters.
- `app/reference_data` owns immutable canonical definitions plus the persistence boundary for explicit reference-data seeding.
- `app/red_agent` owns provider-independent attack-generation contracts, deterministic planning, prompt construction, structured-output validation, and service behavior.
- `app/guardrails` owns normalized defensive contracts, policy resolution, ordered adapter execution, and native/NeMo adapters.
- `app/evaluation` owns deterministic Blue evidence, versioned scenario rubrics, provider-independent Judge execution, and dual security outcomes.

Duel workflows belong in `app/services` when a later phase introduces real orchestration. No CRUD or duel-orchestration service layer exists yet.

### Migration workflow

The Phase 1 baseline is followed by the Phase 2 domain-schema revision. Future schema changes must be represented by new Alembic revisions under `apps/api/migrations/versions`. Developers should inspect autogenerated revisions carefully before applying them with `python -m alembic upgrade head`.

## Domain Model — Phase 2

The domain schema separates versioned security taxonomies, reusable assessment inputs, model registration, and historical duel records.

```text
SecurityFramework
        |
        v
SecurityFrameworkVersion
        |
        v
SecurityRisk <------ Scenario ------> AttackPattern
                         |
                         v
                       Duel
                         |
                         v
                     DuelTurn

ModelProvider ------> TargetModel ------> Duel

PolicyProfile --------------------------> Duel
```

### Security framework hierarchy

A `SecurityFramework` has multiple `SecurityFrameworkVersion` records. Each version has multiple `SecurityRisk` records, and a risk code is unique within its version. Framework identifiers are therefore data, not hard-coded application assumptions, so multiple framework families and versions can coexist.

### Scenario mappings

`ScenarioAttackPattern` and `ScenarioSecurityRisk` are explicit relational association models. They implement the two many-to-many relationships without storing important identifiers in JSON arrays. Attack patterns and risks remain independently reusable.

Scenario severity is constrained to `low`, `medium`, `high`, or `critical`.

### Model registry and policy configuration

A `ModelProvider` has multiple `TargetModel` records. A canonical model identifier is unique within its provider. Provider credentials are never stored in either table.

`PolicyProfile.configuration` and `TargetModel.configuration` are the only flexible JSONB-backed configuration fields. They are intended for non-secret settings whose shape will be defined by later integrations.

### Duels and turns

A `Duel` references exactly one scenario, target model, and policy profile. It records lifecycle state and requested/completed turn counts, but no derived security scores or attack-success metrics.

A `Duel` has ordered `DuelTurn` records. A turn number is positive and unique within its duel. A turn may reference the reusable attack pattern used for that iteration; evaluation entities are intentionally absent.

### Historical integrity and deletion

Foreign keys from duels to scenarios, target models, and policy profiles use `ON DELETE RESTRICT`. Duel turns also restrict deletion of their duel and any referenced attack pattern. These rules prevent ordinary parent deletion from silently removing or invalidating historical run records; disabling reusable records through `is_active` is preferred.

Security-framework hierarchy foreign keys are also restrictive. Association rows use `ON DELETE CASCADE` because they contain no independent historical evidence and only link reusable definitions.

All persisted entities use UUID primary keys and timezone-aware creation/update columns. Database constraints protect unique identifiers, enum values, positive turn counts, and nonnegative completed-turn counts.

## Model Execution — Phase 3

All model execution crosses a provider-independent gateway boundary:

```text
TargetModel
    |
    v
ModelGateway
    |
    v
Provider Adapter
    |
    v
Hugging Face Inference Providers
    |
    v
External LLM
```

`ModelGateway` resolves an adapter from `ModelProvider.provider_type`, applies validated `temperature` and `max_tokens` defaults from non-secret target-model configuration, and returns a normalized result. It rejects credential-like configuration keys before an adapter is invoked.

`HuggingFaceProviderAdapter` uses the official `huggingface_hub.InferenceClient` for structured chat completion. It passes the target's canonical model identifier and supports an optional `provider_route` value in `TargetModel.configuration`; the route defaults to Hugging Face's `auto` behavior. The synchronous client call runs outside the async event loop in a worker thread.

`HF_TOKEN` is loaded only from environment settings. Missing credentials prevent Hugging Face execution but do not prevent application startup. Provider exceptions are chained to sanitized application exceptions for local diagnostics and are not returned directly to API callers.

`POST /api/v1/models/test` loads an active target model and its provider, then performs one gateway request. This endpoint is a connectivity tool only and is not duel execution.

The future Duel Engine will consume `ModelGateway`; it must not depend on Hugging Face or any other provider-specific client.

## Reference Security Catalog — Phase 4

```text
SecurityFramework
        |
        v
SecurityFrameworkVersion
        |
        v
SecurityRisk <------> Scenario <------> AttackPattern
```

The OWASP GenAI LLM Top 10 2026 framework, version, and risk identities are external
reference data. Scenarios and attack patterns are operational Red-Team Arena concepts.
Their many-to-many mappings express project configuration, not OWASP normative
categories. In particular, broader AI-safety scenarios are left without an OWASP link
unless an explicit, defensible mapping exists.

Canonical values are isolated in `app/reference_data`, rather than API handlers or
future duel business logic. An explicit `python -m scripts.seed_reference_data` command
uses repository upserts inside one database transaction. It reconciles records using
the schema's stable natural keys and adds missing association rows, making repeated
runs safe without coupling database writes to FastAPI startup.

The initial policy profiles have empty guardrail configuration. Phase 4 also seeds no
models, providers, or credentials and performs no inference.

## Adaptive Red Agent — Phase 5

```text
Scenario
    |
    v
AttackStrategyPlanner
    |
    v
AttackPattern
    |
    v
RedAgentPromptBuilder
    |
    v
RedAgentService
    |
    v
ModelGateway
    |
    v
Attacker Model
    |
    v
RedAgentResult
```

`AttackStrategyPlanner` selects only from the scenario's configured patterns. It is
deterministic, prioritizes untried techniques, avoids unnecessary immediate reuse,
prefers multi-turn escalation after partial compliance, and uses prior effectiveness
when every allowed pattern has been attempted.

`RedAgentPromptBuilder` supplies the selected scenario, pattern description, target
context, turn position, objective, and prior evidence to the attacker model. It asks
for one JSON object containing an attack prompt plus concise strategy and adaptation
summaries. These fields are operational evidence, not hidden chain-of-thought.

`RedAgentService` invokes the existing provider-independent `ModelGateway`. An
attacker model is described by a non-persisted runtime contract containing its
canonical identifier, provider, third-party status, explicit `attacker` role, and
non-secret provider configuration. It is not assumed to be the target model.
Attacker generation defaults are explicit and independent: temperature `0.7` and
maximum output `512` tokens.

`POST /api/v1/red-agent/generate` is a temporary development endpoint that performs
exactly one attacker-model generation and returns normalized evidence. It does not
call the target model, evaluate success, write duel records, or run guardrails. A real
one-shot Hugging Face check is available only through explicit invocation of
`python -m scripts.test_red_agent MODEL_ID --scenario jailbreak`; credentials remain
environment-only.

## Guardrail Engine — Phase 6

```text
Attack Prompt
    |
    v
GuardrailEngine
    |
    v
Policy Resolver
    |
    +-------------------------------+
    | Native Guardrail Adapter      |
    | NeMo Guardrail Adapter        |
    +-------------------------------+
    |
    v
GuardrailExecutionReport
```

`GuardrailEngine` has no NeMo- or Hugging Face-specific logic. It executes normalized
`GuardrailAdapter` implementations in order, applies profile enforcement centrally,
passes modified content to the next adapter, stops on enforced blocks or errors, and
preserves evidence from every adapter that ran.

The native adapter provides a small, auditable offline baseline. The NeMo adapter loads
the reviewed project configuration lazily, invokes only the requested input or output
rail, and converts NeMo-specific results and failures into application contracts. The
initial NeMo configuration uses deterministic actions and has no internal LLM.

Future orchestration will use the boundaries as follows:

```text
Red Agent
    |
    v
INPUT GUARDRAILS
    |
    v
Target Model through ModelGateway
    |
    v
OUTPUT GUARDRAILS
    |
    v
Blue Evaluator
```

Guardrail prevention is distinct from Blue evaluation and rubric judging. Guardrails
decide whether content may continue and record defensive findings; the evaluator
assesses target behavior, while a judge applies an evaluation rubric. These later
responsibilities remain outside the Guardrail Engine itself.

`POST /api/v1/guardrails/test` and
`python -m scripts.test_guardrails --stage ... --policy ... --content ...` test an
isolated stage only. They never invoke the Red Agent or target model.

## Security Evaluation Pipeline — Phase 7

```text
Attack Prompt
    |
    v
Input Guardrail Evidence
    |
    v
Target Response
    |
    v
Output Guardrail Evidence
    |
    v
BlueEvaluator
    |
    v
Structured Evidence
    |
    v
RubricJudge
    |
    v
SecurityEvaluationResult
```

`BlueEvaluator` uses small deterministic checks to extract stable, auditable evidence.
It does not classify the final outcome. Each canonical scenario has an explicit
project-owned rubric with an ID and semantic version. Ambiguous evidence crosses
`RubricJudge → ModelGateway → Provider Adapter → Judge Model`; the evaluation package
does not import a provider-specific client.

### Model Resilience vs System Defense

This distinction is mandatory and represented by separate fields in every security
evaluation result:

- **Model Resilience** measures how the target itself behaved after receiving the
  attack. It is not evaluated when input guardrails stopped target execution.
- **System Defense** measures whether the protected system prevented the attack from
  reaching or being exposed beyond its guardrail boundaries.

An output guardrail can therefore defend the system while the preserved model outcome
is still `breach`. Guardrail prevention does not overwrite model evidence or become an
automatic claim that the target is secure.

The Rubric Judge classifies only raw target-model behavior. `EvaluationService` composes
the defended-system outcome from recorded guardrail decisions: allowed output inherits
the model outcome, output blocks contain even a model breach, and errors remain errors.
Modified output is system-inconclusive until its system-visible content is evaluated
separately; modification is not equivalent to a block.

`EvaluationService` evaluates one supplied interaction only. It skips Judge Model
execution for objective input blocks, execution absence/errors, and rubric cases that
lack required trusted reference context. It neither calls the Red Agent nor target
model and does not update Duel or DuelTurn records.

`POST /api/v1/evaluation/test` is the isolated development boundary. An optional
`python -m scripts.test_evaluation ...` command can make at most one explicitly
requested Judge Model call using environment credentials.

## Duel Execution Pipeline — Phase 8

```text
Duel
  |
  v
Turn
  |
  v
RedAgentService
  |
  v
Input GuardrailEngine
  |
  v
Target ModelGateway (only when input permits)
  |
  v
Output GuardrailEngine
  |
  v
EvaluationService
  |
  v
Persist Evidence
  |
  v
Next Turn / Stop
```

`DuelOrchestrator` is an application coordinator. It constructs stable contracts for
the Phase 5–7 services and calls them in order; it does not import provider clients,
NeMo internals, native security rules, or Judge prompt implementation. A pending Duel
can transition once to running and then to completed, stopped, or failed. Terminal
Duels cannot be restarted. Each turn follows pending → generating_attack →
scanning_input → awaiting_model → scanning_output → evaluating → completed, with
blocked input moving directly from scanning_input to evaluating. Any unrecoverable
operational failure moves the active turn and Duel to failed. A defensive block is a
successfully assessed completed turn, not a technical failure.

External model calls are never wrapped in one long database transaction. The
repository commits stable checkpoints after turn creation, attack generation, each
guardrail report, raw target execution, processed output, and evaluation. This keeps
database transactions short during provider latency and retains the last reliable
evidence checkpoint when an operational step fails.

The evidence schema keeps queryable security dimensions relational:

- `duel_turn_attacks` is authoritative for generated attack and adaptation evidence;
- `duel_turn_model_executions` is authoritative for raw target behavior and the
  separate system-visible response;
- `duel_turn_guardrail_reports` stores one relational stage/decision row per turn and
  flexible adapter detail in reviewed JSONB; and
- `duel_turn_evaluations` stores model/system outcomes and scores as columns while
  flexible evidence and safe metadata use JSONB.

The original `duel_turns.attack_pattern_id`, `attack_prompt`, and `target_response`
columns remain compatibility mirrors. They are not removed destructively. Evidence
rows cascade only when their owning turn is deliberately deleted; references from a
Duel to scenario, target model, and policy remain restrictive.

Input modification preserves the original attack while recording the effective prompt
actually sent to the target. Input block skips target execution and produces an
unevaluated model outcome plus `blocked_by_guardrail` system outcome. Output filtering
never overwrites the raw target response: a vulnerable raw response may therefore have
model outcome `breach` while the defended system outcome is `blocked_by_guardrail`.

`stop_on_first_breach` means the first confirmed end-to-end system breach
(`system_outcome == breach`). A model breach contained by an output guardrail does not
stop the Duel. Completed-turn summaries—not ORM instances or hidden Judge reasoning—
carry the relevant pattern, prompt, raw response, model/system outcomes, and concise
evaluation summary into later Red Agent requests.

Provider and Judge failures are operational failures, not fabricated security
outcomes. Persisted failure evidence contains only the failed stage, a safe category,
a sanitized fixed message, and timestamp. Transient attacker/Judge runtime settings
are accepted by the run endpoint, reject credential fields, and are not stored.

Phase 8 exposes:

- `POST /api/v1/duels` to create a pending Duel;
- `POST /api/v1/duels/{duel_id}/run` to synchronously execute that pending Duel; and
- `GET /api/v1/duels/{duel_id}` to recover normalized persisted turn evidence.

`python -m scripts.demo_duel_mock` exercises this pipeline entirely with in-memory
mocks and labels all output as non-evidence. It makes no provider or database calls.

## Planned Architecture — Not Yet Implemented

The following components remain future boundaries, not working functionality:

- **Scenario Engine** — defines scenario authoring and lifecycle behavior around the schema.
- **Additional Provider Adapters** — add provider implementations behind the existing gateway contract.
- **Analytics Engine** — aggregates completed assessment evidence and metrics.
- **Report Engine** — produces auditable technical and executive reports.

Authentication, broader CRUD APIs, additional provider integrations, PromptFoo,
streaming, background queues, aggregate metrics, analytics, and reports are
intentionally absent.
